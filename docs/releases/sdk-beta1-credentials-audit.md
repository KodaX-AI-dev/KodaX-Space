# beta.1 的凭证改动，Space 是否完整接入？

2026-11-03，审计固定点 Space `64fcfed3`；已安装 SDK `0.7.97-beta.1`。结论：模型 Provider 新 API Key、默认 OAuth 和 Main 稳定秘密已经采用文件路径，无需 Keychain；但设置仍错误宣称系统加密存储，来源选择不能完整表达“已批准的 env”，Partner 连接器也仍依赖旧 Keychain。不能将当前实现描述为整个 Space 已摆脱 Keychain。以下只读源码、文档和隔离假凭证 probe，不读取真实凭证、不改生产代码、不切换原生 ABI。[版本](../../node_modules/@kodax-ai/kodax/package.json#L3)、[依赖](../../package.json#L59)、[文件入口](../../apps/desktop/electron/providers/provider-storage.ts#L87)、[连接器入口](../../apps/desktop/electron/partner-connectors/runtime.ts#L21)。

## 已确认的必要修正

### P1：阻止未经批准的新环境账号接管；保留已明确批准的环境回退

强复现使用正式已安装 SDK 和 Space 公开 Main 凭证函数、独立临时数据根与假值：首次不存在 env，保存并固定文件账号 A；随后 env B 出现，由另一个 SDK store 删除 A（不走 Space UI/删除动作）；Space 可读到 `scope:'shared'`、删除墓碑、`configured:false`，但下一次 `readProviderCredential()` 返回 B。临时目录已删除，只输出布尔，不输出秘密。脚本：`artifacts/diagnostics/beta1-release/credential-external-removal-audit.mjs`。实现原因是 file adapter 返回 undefined 后 `credentials.ts:228-229` 无条件读取 env；选择记录 v1 只保存 scope 和 connectionFingerprint，不能表达 env 的批准事实。[file-credentials:45-58](../../apps/desktop/electron/providers/file-credentials.ts#L45)、[credentials:228-229](../../apps/desktop/electron/providers/credentials.ts#L228)。

这违反已安装 SDK 对 Space 的“删除/原来源不可用不能静默换号”接手要求，以及当前用户手册的承诺。[SDK migration:623-625](../../node_modules/@kodax-ai/kodax/docs/SDK_MIGRATION.md#L623)、[用户手册:689](../USER_MANUAL.zh-CN.md#L689)。不过已有产品合同也明确允许 **已经批准的 env 回退**，且 ProviderCard 在 `both` 时会提示删除后使用 env；不能将这个有提示的正常路径也一并禁掉。[现有凭证合同:62-65](../SDK_PROVIDER_CREDENTIALS.md#L62)、[ProviderCard:279](../../apps/desktop/renderer/src/features/provider/ProviderCard.tsx#L279)、[文案:5007](../../apps/desktop/renderer/src/i18n/messages.ts#L5007)。

最小方案（设计建议，尚未实施）：

1. 升级 Space 私有 selection 为 v2，在 scope/fingerprint 之外持久记录实际已批准来源 `file/env/legacy`；区分“可用环境变量”与“已授权使用环境变量”。env 仅记录变量名/来源，不复制其值；Legacy 成功复制时与原值/来源一起 CAS 转换为 file。承接的是已有三个实际来源，不新增第二 credential writer。[现有同批 CAS 能力](../../apps/desktop/electron/providers/file-credentials.ts#L155)、[SDK AtomicFile 契约](../../node_modules/@kodax-ai/kodax/docs/SDK_MIGRATION.md#L620)。
2. 已选 file 值不存在/出现墓碑时，默认返回原来源不可用，不能让 undefined 变成通用 env 许可。已选 env 继续读取原变量；缺失时不采用共享 Key。显式“使用环境变量”或显示时已明确告知并批准的“删除并使用现有 env”才能 CAS 改来源；原 CLI 自身默认的“删保存值后显示 env”不改。[Space 原来源合同](../SDK_PROVIDER_CREDENTIALS.md#L37)、[SDK CLI 默认规则](../../node_modules/@kodax-ai/kodax/docs/SDK_MIGRATION.md#L544)。
3. v1 选中记录仍有实际 Key 时，可无歧义升级为 file；已固定 shared 后只有删除墓碑，可保留 file-unavailable 状态。**v1 private/space 的空值或墓碑存在歧义：既可能是 env pin，也可能是文件删除，不能靠当前 env 存在、时间戳或读取旧备份猜测。** 保留原记录并展示待确定来源；用户明确继续 env 或重新保存 Key 后再更新 selection，不覆写墓碑，不让旧备份复活。[v1 env pin](../../apps/desktop/electron/providers/file-credentials.ts#L106)、[v1 remove](../../apps/desktop/electron/providers/file-credentials.ts#L170)、[v1 selection schema](../../apps/desktop/electron/providers/file-credentials.ts#L48)。
4. Provider list、Card、测试按钮、Run broker 和所有辅助 SDK 操作消费同一来源决策，显示有效来源与不可用状态，不仅根据 env 存在或 `hasKey` 推导 configured。显示时状态仍用于 CAS，不能为删/改读取新 revision 代替用户原状态。[当前分散投影](../../apps/desktop/electron/ipc/provider.ts#L176)、[当前 detailed 合并](../../apps/desktop/electron/ipc/provider.ts#L237)、[当前实际 broker](../../apps/desktop/electron/providers/runtime-credential-broker.ts#L38)。

验收：先 RED 固定上述外部 SDK 删除 + 后出现 env 的 case；覆盖 private/shared、重启、CLI 并发写、迟到迁移、旧 v1 歧义、approved env 正常删除回退、新用户首次 env、env 消失、地址变化、强制撤销。任何未知来源都不请求模型；显式动作后使用所选账号且不泄露 Key；仍可同根共享文件而分账号。[已有升级测试](../../apps/desktop/electron/providers/file-credentials.upgrade.test.ts#L133)、[现有实际成品 env/CLI 分离测试](../../tests/e2e/provider-file-credentials.spec.ts#L84)。本轮 probe 不声称复现“用户已经看到 both 提示并点击删除”路径的缺陷。

### P1：修正真实存储方式的 UI 和操作提示

Main 已返回 file，但 Settings 的非 memory 分支始终展示 Keychain / OS-protected encrypted storage；Storage 一栏也固定说 API Key 使用系统凭据加密。CustomProvider 保存提示仍称系统存储并向 env 注入。这些用户能看见的保证与实际权限保护明文 auth.json 不一致，需要中英文同时改为“权限保护的凭证文件（auth.json）”，实际根由 Main 非秘密状态返回或明确说明跟随当前数据档。不能说新文件是加密的，也不能因系统 Keychain 不可用提示新 Key 重启丢失。[SettingsModal:2823-2830,2973](../../apps/desktop/renderer/src/features/settings/SettingsModal.tsx#L2823)、[i18n:2076-2078,2100-2101,4964-4986,5082-5083](../../apps/desktop/renderer/src/i18n/messages.ts#L2076)、[实际后端](../../apps/desktop/electron/providers/provider-storage.ts#L282)。

## Keychain 仍然承担的范围

Partner 连接器并未因 Provider 升级自动迁移：基础 runtime 使用 `keychain.get/set/delete` 构造 verified store（邮件、Tencent 等）；官方远端连接器同样默认 keychain，供 Notion/Airtable/Atlassian/Slack/GitHub/Zoom 等连接使用。[基础 runtime:21-26,107-115](../../apps/desktop/electron/partner-connectors/runtime.ts#L21)、[官方 runtime:215-217,302-357](../../apps/desktop/electron/partner-connectors/official-remote-runtime.ts#L215)。这是实际仍会发生的新秘密写入，不是只读旧迁移；因此目前不能删除 `@napi-rs/keyring` 或旧 storage 文件。[Keychain set 实现](../../apps/desktop/electron/providers/keychain.ts)、[既有合同明确保留 Partner 账户](../SDK_PROVIDER_CREDENTIALS.md#L11)。

方案建议：若产品目标是**整个 Space 不需要 Keychain**，把连接器秘密作为单独切片，沿现有 CredentialStore 端口替换默认后端，使用 Main 私有命名空间和明确 connection/account 身份，按需导入原账号、保留旧加密备份、删除墓碑优先、失败不产生新账号。Provider auth 命名空间与 connector 凭证分开，不能把 connector OAuth token 冒充 Provider OAuth registration。要先确认 SDK 文件后端是否正式支持这一命名空间/任意秘密契约；若无此保证，再选择最小 Space 专用持久文件或请求 SDK 配合，而非直接把 token 写入普通 config。该切片属于 Space 自有连接器能力，不宜假称是 beta.1 Provider API 的强制迁移。[现有端口](../../apps/desktop/electron/partner-connectors/official-remote-runtime.ts#L199)、[现有实现](../../apps/desktop/electron/partner-connectors/runtime.ts#L26)。

## 尚缺验证、可选能力与未证实

- OAuth 消费可用，但 Space 当前 Provider UI 没有 SDK 原生 login/logout 流程；仍按既有合同交给 SDK/CLI/config。若“可用”要求桌面内完成订阅登录、换号、退出和状态恢复，需要单独实现 UI/IPC，不能算已接完；仅存在 OAuth badge 不等于登录验收。[ProviderCard:35-145](../../apps/desktop/renderer/src/features/provider/ProviderCard.tsx#L35)、[既有高级配置边界](../SDK_PROVIDER_CREDENTIALS.md#L23)。
- 凭证文件 binding 使用 default namespace，而 Runtime 的执行角色为 coder，原合同明确这两个概念不同；不能为了追求“profile一致”把现有共享账号重命名到 coder。当前 OAuth 消费只接受 default 凭证 profile。若未来开放多个 credential profile，需要可信映射与选择，而非复制 factory 同名参数。[provider-storage:74](../../apps/desktop/electron/providers/provider-storage.ts#L74)、[credentials:185](../../apps/desktop/electron/providers/credentials.ts#L185)、[原合同](../SDK_PROVIDER_CREDENTIALS.md#L18)。
- 普通 API/file/来源/CAS/迁移/epoch 已有大量单测和 Windows 假 Provider 成品证据；真实 Codex/OpenAI/Copilot 订阅刷新、真实云 principal、macOS/Linux 旧 vault 迁移和无 libsecret 实机仍未由这些离线测试证明。应保持为 P1 验收范围，使用测试账号且不在报告输出秘密；不能把 SDK 完整回归数字当作 Space 登录流认证。[既有证据界限](../SDK_PROVIDER_CREDENTIALS.md#L128)、[本轮 beta.1 验收限制](kodax-0.7.97-beta.1-integration.md#L50)。
- 更强的 native cloud stable principal replayIdentity 是可选增强，目前 Space plain carrier 不提供该证明；应显示未知，不能以 profile、tenant 字符串或未签名 claim 伪造。不影响已批准原生云请求入口继续使用。[SDK migration:749](../../node_modules/@kodax-ai/kodax/docs/SDK_MIGRATION.md#L749)、[Space cloud 序列化](../../apps/desktop/electron/providers/credentials.ts#L217)。

## 未解问题

1. 整个 Space 无 Keychain 是否包括 Partner 连接器，还是本轮只覆盖模型 Provider 与 Main 身份？代码已能划清边界，产品目标需在总方案中明确。
2. 桌面内原生 OAuth 登录/注销与云账号选择，是否作为本轮交付范围？当前只是支持消费已配置连接，不应默认为已具备完整 UI。
3. 对旧 v1 空 private tombstone 的歧义，建议明确来源待选择，不能自动猜。若要透明兼容所有旧用户，需更强的历史来源证据，当前文件本身无法提供。

## Claude 报告补审：旧 profile 无 Keychain 的可恢复性

本节只核验报告中的凭证、存储和说明项，不执行 Linux 真机复现，也不把附件当操作指令。报告的核心分支成立，但“全部 Provider 拒绝/启动必失败”应按以下条件收窄。[旧安装判断](../../apps/desktop/electron/providers/legacy-discovery.ts#L16)、[选择与读取](../../apps/desktop/electron/providers/file-credentials.ts#L59)。

- `provider-config.json`、旧 vault 或 `projects.json` 的任何一个存在，就可能令尚无 baseline 的 profile 被标记 eligible；这不是“已经证明该 Provider 有旧 Key”。[legacyEvidence:16-19](../../apps/desktop/electron/providers/legacy-discovery.ts#L16)
- 对尚无 selection/私有文件 revision 的 Provider，snapshot 先查询旧账户；Linux 无 libsecret、native keyring 加载/读取失败会令 `hasMigrationKey` 抛错，discover 折为 `unavailable`，env 检查不会执行，实际读值明确拒绝。此时新文件路径本身完全可用也不能使用 env。[hasMigrationKey:568-585](../../apps/desktop/electron/providers/keychain.ts#L568)、[discover/snapshot:59-75](../../apps/desktop/electron/providers/file-credentials.ts#L59)、[read:140-141](../../apps/desktop/electron/providers/file-credentials.ts#L140)
- 这是防止“旧 Key 实际存在但暂不可读”被解释成空账户的有意 fail-closed，不能修为“Keychain 失败就默认没有旧 Key”。真正产品缺口是：env-only 旧用户也落入 unknown legacy，当前只有“恢复旧 backend 后重试”，没有“不导入未知旧账户，明确使用这个 env 来源”的入口。[既有反回退测试:229-239](../../apps/desktop/electron/providers/file-credentials.test.ts#L229)、[ProviderCard 的迁移说明与可用动作:258-279](../../apps/desktop/renderer/src/features/provider/ProviderCard.tsx#L258)
- 影响范围不是整个 profile 所有能力：fresh baseline、已由 Space 持久选择的文件账号、已持久 pin 的 env/shared 跳过该 discover；尚未被 Space 选择的 CLI 共享文件 Key 不等于这一条件。`describe` 可返回 unavailable 状态，通常是在测试连接、真实请求/需要 credential 的操作中拒绝，并非读状态或普通启动必抛。手工显式保存新 Key、或已有共享 Key 的显式 adopt 也可能绕过后续旧发现。`injectAllKeysToEnvUnlocked` 目前只恢复旧 managed env 并初始化 file backend，不再逐 Provider 读 Key。[snapshot:70-74](../../apps/desktop/electron/providers/file-credentials.ts#L70)、[set/share:162-188](../../apps/desktop/electron/providers/file-credentials.ts#L162)、[启动兼容函数:139-142](../../apps/desktop/electron/ipc/provider.ts#L139)

可实施方案：并入切片 A 的来源 v2，保留 unknown legacy 与原材料；由 Main 返回非秘密的 `migrationUnavailable`、当前可用 env 变量名和只读修复状态。在 ProviderCard/自定义配置中提供明确的“重试旧凭证”“使用现有环境变量”“保存新 Key”，共享 Key 存在时继续已有 adopt。用户明确选择 env 后，以完整原显示 binding/selection/shared/private revision 进行 CAS，持久记录 origin=env，保留旧备份及墓碑；仅改变该 Provider 的授权来源，不全局关闭 legacy discovery，不复制 env 值，也不为别的 Provider 自动同意。env 缺失则保留选择、明确不可用。并发旧来源恢复、CLI 更新或地址变更时按原 CAS 冲突处理，不回读新 revision 强行完成。[现有 CAS](../../apps/desktop/electron/providers/file-credentials.ts#L82)、[现有显式共享动作](../../apps/desktop/renderer/src/features/provider/ProviderCard.tsx#L108)、[既有来源契约](../SDK_PROVIDER_CREDENTIALS.md#L37)。

验收要覆盖旧 profile（仅旧 settings/projects、确有旧 Key、旧 backend 不可用、当前 file 已迁好、原 env pin）与 fresh profile，在无 libsecret fixture/真实 Kylin 上分别验证；用户未选择时不派发，显式 env 选择后使用 env、重启仍保留、恢复旧库后不自动换回，其他 Provider 不受影响。**Provider 选择 env 不等于恢复 Main 稳定身份**：若 active/exitRecovery 原 secret 仍只在不可读旧库，必须单独恢复原身份/走有证明的修复，不生成新 identity 掩盖失败。测试需区分“Main secret 已在 auth.json”和“Main secret 旧库仍不可读”。[稳定秘密读取:40-52](../../apps/desktop/electron/kodax/runtime/runtime-client-secret-file.ts#L40)、[旧持久读取要求:211-240](../../apps/desktop/electron/providers/keychain.ts#L211)。

## Claude 报告补审：连接器降级和外部 CLI 的存储边界

“连接器还用 Keychain”是抽象端口，不代表所有平台都将 token 直接放进 OS keyring：正常 Windows/macOS 使用 Electron safeStorage 保护的加密 vault 文件，Linux 一般走原生 keyring。初始后端已经降为 memory、macOS 某些 vault 写失败或 Linux keyring 写失败时，`setKey` 会把值放进 memory 并成功返回；Windows 已选持久 vault 后的写失败则由 `setPersistentKey` 抛错，不宜把各平台概括成完全相同的降级路径。[detectBackend:124-161](../../apps/desktop/electron/providers/keychain.ts#L124)、[setKey:264-313](../../apps/desktop/electron/providers/keychain.ts#L264)、[setPersistentKey:242-257](../../apps/desktop/electron/providers/keychain.ts#L242)。

这个降级有部分 `console.warn`，所以不是“完全无日志”；但连接器的 `CredentialStore.set` 只返回 void，verified wrapper 只对**删除**做回读核验，未携带 durable/backend 状态。Provider IPC 已恒返回 file，因此 Providers 页的 memory-only 警告不会替连接器揭示此降级。静态链路支持“用户可能看到连接成功，但重启后原 secret 消失且没有持久性提示”；本轮未做真实 Linux connector 登录复现。[wrapper:199-217](../../apps/desktop/electron/partner-connectors/official-remote-runtime.ts#L199)、[API 凭证保存:86-91](../../apps/desktop/electron/partner-connectors/api-credential-connector.ts#L86)、[OAuth 保存:427](../../apps/desktop/electron/partner-connectors/remote-mcp-oauth.ts#L427)、[Provider backend:282-285](../../apps/desktop/electron/providers/provider-storage.ts#L282)、[旧警告:2878](../../apps/desktop/renderer/src/features/settings/SettingsModal.tsx#L2878)。

最小产品修正是让连接器自己的保存结果包含持久/临时/失败事实，临时保存必须明确告知仅当前进程、重启须重新连接，或在要求持久账号时明确拒绝；不能继续仅凭同进程 get 成功称 durable。彻底去 Keychain 的连接器切片再按原账号、来源、撤销和备份规则迁文件后端。[当前通用 storage 端口](../../apps/desktop/electron/partner-connectors/remote-mcp-oauth.ts#L14)、[已有连接器账号隔离要求](../partner/features/f146-official-office-connectors.md#L24)。

关于“只有连接器新写 Keychain”：**准确限定是生产路径中只有这两组连接器调用旧封装 `setKey` 保存新认证材料**；Provider 自己的同名 setKey 已走 file。不能扩大成“其他链路绝不写旧 vault”：Main/Provider 的按原 secret 迁移读取可能调用 `vault.importLegacy`，Windows 有证明的旧解密恢复可能调用 `vault.recover`，它们仍写回同一原值，不是新认证。[新写 callers](../../apps/desktop/electron/partner-connectors/runtime.ts#L21)、[官方 callers](../../apps/desktop/electron/partner-connectors/official-remote-runtime.ts#L215)、[旧读取副作用:219-241](../../apps/desktop/electron/providers/keychain.ts#L219)。

钉钉属于第三种边界：**官方 CLI 自管认证**，不是 Space `keychain.ts` 或 SDK Provider auth.json。Space 目前只开放 macOS ARM64，生成私有 profile，设置 `DWS_CONFIG_DIR`/`DWS_KEYCHAIN_DIR`；自己写的 `binding.json` 仅为经在线核实的企业/用户身份摘要，实际 token 由 `dws auth login` 保存。[Space profile:51-54,94-99](../../apps/desktop/electron/partner-connectors/dingtalk-connector.ts#L51)、[平台/CLI overrides:174-188](../../apps/desktop/electron/partner-connectors/dingtalk-connector.ts#L174)、[登录与 binding:293-304](../../apps/desktop/electron/partner-connectors/dingtalk-connector.ts#L293)。官方固定 v1.0.61 的 macOS 实现把 token 密文写在该目录，同时默认通过系统 Keychain 读取/创建 `dek`；隔离目录不等于去掉系统 Keychain。不能为达成全应用无 Keychain 而偷偷启用官方 CLI 的测试用 file-DEK bypass；应单列外部 CLI 能力/限制并按其公开契约迁移。[官方 StorageDir 与 DEK](https://github.com/DingTalk-Real-AI/dingtalk-workspace-cli/blob/v1.0.61/internal/keychain/keychain_darwin.go#L42)、[官方 DEK](https://github.com/DingTalk-Real-AI/dingtalk-workspace-cli/blob/v1.0.61/internal/keychain/keychain_darwin.go#L248)、[官方原子密文写入](https://github.com/DingTalk-Real-AI/dingtalk-workspace-cli/blob/v1.0.61/internal/keychain/keychain_darwin.go#L409)、[官方 token 保存](https://github.com/DingTalk-Real-AI/dingtalk-workspace-cli/blob/v1.0.61/internal/auth/keychain_store.go#L107)。
