# deepseek-harness 如何加载、渲染并浏览会话历史？

结论摘要：最值得借鉴的是“历史与实时输出共用连续窗口、按内容身份保持阅读位置、用户主动离开底部后保留阅读控制权”。该项目普通 Chat 正文仍逐项挂载，旧记录通过按钮加载；Trajectory 技术轨迹视图另有表行虚拟化与顶部自动加载。不能把后者的能力算到普通 Chat，也不能把分页上限当成整个会话的内存上限。证据分别见下文加载、位置与双视图部分。

## 一、普通 Chat 的历史加载

1. **先打开尾部窗口，随后向前扩展。** `open()` 幂等复用正在进行的打开；`doOpen` 使用同一组历史页选项打开事件流。默认每页以至少 50 条消息、跨至少 2 个 Turn 起点为目标，上限 500 条消息；跳转加载每页最少 200 条。这里消息计数指 append-origin 用户/助手消息，不能直接解释为 50 个 DOM 行、50 个事件或固定字节数；遇到历史耗尽或 500 上限可提前结束 Turn 对齐。来源：[session.ts:52](C:/Works/PubProj/deepseek-harness/packages/api/session-controller/src/client/sessions/session.ts:52)、[session.ts:406](C:/Works/PubProj/deepseek-harness/packages/api/session-controller/src/client/sessions/session.ts:406)、[session.ts:632](C:/Works/PubProj/deepseek-harness/packages/api/session-controller/src/client/sessions/session.ts:632)、[types.ts:472](C:/Works/PubProj/deepseek-harness/packages/api/session-controller/src/types.ts:472)。
2. **普通 Chat 使用“加载更早”按钮。** `hasMore` 时显示按钮，`loadingOlder` 时禁用并改为加载文案；按钮调用 `loadEarlier → beginPaging → pauseFollowing → loadOlder`。本次检查的 ChatView 与滚动协调代码没有顶部自动分页调用，不能从别的视图推断 Chat 支持自动加载。来源：[ChatView.tsx:239](C:/Works/PubProj/deepseek-harness/packages/client/ui-chat/src/client/chat/ChatView.tsx:239)、[use-chat-navigation.ts:93](C:/Works/PubProj/deepseek-harness/packages/client/ui-chat/src/client/chat/use-chat-navigation.ts:93)、[use-chat-scroll.ts:106](C:/Works/PubProj/deepseek-harness/packages/client/ui-chat/src/client/chat/use-chat-scroll.ts:106)。
3. **单页加载防重入，跨页跳转合并发布。** `loadOlder` 在未打开、无更多历史或正在加载时退出；`loadThrough(seq)` 循环向前读，已有跳转则共享 Promise 并取更早目标。跳转期间旧页暂存，完成或后续页失败后将成功页一次 prepend；检测代际变化及页无进展，避免旧请求污染新窗口或无限循环。实时 append 仍直接发布。来源：[session.ts:418](C:/Works/PubProj/deepseek-harness/packages/api/session-controller/src/client/sessions/session.ts:418)、[session.ts:440](C:/Works/PubProj/deepseek-harness/packages/api/session-controller/src/client/sessions/session.ts:440)、[session.ts:737](C:/Works/PubProj/deepseek-harness/packages/api/session-controller/src/client/sessions/session.ts:737)；对应断言：[session.client.spec.ts:274](C:/Works/PubProj/deepseek-harness/packages/api/session-controller/tests/session.client.spec.ts:274)、[session.client.spec.ts:312](C:/Works/PubProj/deepseek-harness/packages/api/session-controller/tests/session.client.spec.ts:312)。
4. **页上限不是常驻窗口总上限。** `prependWindow` 对 eventSource 执行 prepend；普通 Chat 的 `ChatFlow` 对全部当前 entries 做 map，组内成员也全部 map。本次检查路径未见“加载一页、卸载另一页”的正文窗口淘汰。因而可证实分页限制单次读取，不能据此声称整个长会话固定内存或正文已虚拟化。来源：[session.ts:738](C:/Works/PubProj/deepseek-harness/packages/api/session-controller/src/client/sessions/session.ts:738)、[ChatFlow.tsx:52](C:/Works/PubProj/deepseek-harness/packages/client/ui-chat/src/client/chat/ChatFlow.tsx:52)、[ChatGroupSeat.tsx:86](C:/Works/PubProj/deepseek-harness/packages/client/ui-chat/src/client/chat/ChatGroupSeat.tsx:86)。

## 七、对 KodaX Space 的可借鉴项与真实权衡

以下是基于前述实现的设计建议，尚未核验 KodaX Space 的实现成本，不作为它已有/缺失能力的事实。

| 建议 | 借鉴理由 | 代价或适用边界 |
| --- | --- | --- |
| 先统一历史页、live、最终记录的稳定消息身份 | baseline/attempt/seq 与 requestId 去重让显示衔接有明确依据，参见第二节 | 需要数据模型提供可靠身份与结算语义；不要复制其整套 Cordis projection/slot 架构才能解决局部问题 |
| 保存消息锚点+相对高度，保留 raw scrollTop 作为后备 | 应对 prepend、宽度重排和异步变高，参见第三节 | 消息被删或虚拟化卸载时需加载/定位策略；嵌套过程区还需内外滚动协调，单纯保存像素不够 |
| 明确区分“跟随最新”和“正在读历史” | 避免 live 抢阅读位置，返回最新可以显式重新取得跟随控制，参见第三节 | 判断 reader input、浏览器 clamp、程序滚动及折叠动画会增加复杂度；可先覆盖 Space 实际存在的路径 |
| 顶部自动加载可借鉴 Trajectory，保留按钮与忙态 | 自动加载减少连续回看的操作，按钮提供显式控制，参见第五节 | 普通 Chat 自己选择手动加载；自动分页要处理短内容、重复触发、锚点补偿与请求上限，不能照搬一个 onScroll 即认为完成 |
| 按用户阅读目标提供 Turn 导航或有限搜索 | 未加载 Turn 可先展示 outline，再按需获取正文，参见第三节 | 此项目跳远处仍逐页取齐中间记录，距离越远请求/累计数据可能越多；若 Space 需要任意命中跳转，应另评估目标周边窗口接口 |
| 先做稳定行、增量 Markdown、延迟高亮，再按证据决定正文虚拟化 | 这些优化分别作用于无关行重渲染、单条长回复解析和屏外高亮，参见第六节 | 保持挂载有利于选择、焦点、浏览器查找，却不能限制长会话 DOM；Trajectory 固定高度 ledger 的虚拟化经验不能直接移植到可变高度 Markdown 正文 |
| 折叠异常保持可见，折叠策略先少后多 | 源码区分异常 Turn、过程与最终答复，参见第四节 | 多种 detail/timing/reply 偏好使状态组合与滚动测试增多；Space 未有同等需求时，不宜一次复制所有设置 |

## 未解问题

1. Space 的主目标是连续向前回看、按 Turn 定位，还是跨会话全文命中跳转？三者决定“连续窗口”与“目标周边窗口”接口是否足够。
