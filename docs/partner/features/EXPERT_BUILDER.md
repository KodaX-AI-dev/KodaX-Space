# Partner 专家开发方法

PF007 建立统一专家模型。岗位、任务是发现入口；平台操作通过连接器提供。新增专家前，先回答它要做什么判断、产出什么可验收结果。只有服务操作差异的需求进入连接器；只有可复用步骤的需求进入 Skill。不要为每个连接器再创建同名专家。

## 会话持续绑定

2026-09-07 用户进一步明确：专家采用挂载到当前对话的配置包思路，由当前 Partner Agent 持续使用专家的角色、方法和交付标准。专家能力的完整性按实际任务结果衡量，不按 Skill 数量或编排复杂程度衡量。

- 挂上专家后，该会话后续对话与任务持续使用已保存的专家配置；每轮注入，不能仅在首次消息里拼接一次提示词。
- 岗位专家与任务专家具有相同的绑定生命周期。任务专家也不会在完成一个任务后自动移除；名称描述专业范围，不决定会话时长。
- 用户明确切换或移除专家后，新配置从后续运行生效。正在执行的运行保持已捕获的配置；历史消息、资料和成果仍保留。
- 切换会话时加载该会话自己的绑定，恢复会话时保留原专家版本和 Skill 开关。新对话沿现有独立选择规则，不继承上一会话的专家。
- 专家默认方法持续可用；关闭默认 Skill 仍保留专家角色。用户显式调用其他 Skill 时，按现有优先级用于该次任务，不清除专家绑定。
- 当前专家复用会话的上下文、执行器和已授权连接器。独立子 Agent 的上下文、记忆、调度与小队协作属于另一项能力，不作为本轮专家完善的默认方向。
- 持续对话应沿用已有事实和决策，按当前问题裁剪方法和交付检查；简短追问不重新收集全部背景，也不强制生成完整报告。宿主 `partner-profile.ts` 统一注入这条规则，不要求各专家重复维护。
- 输入框展示持续使用提示，读取会话配置时展示加载状态；不可用时保留绑定并说明原因。旧详情页使用“选择后”说明，不能冒充当前已绑定专家。

对应接缝是 `real-session.ts` 的每轮专家捕获及方法准备、`partnerExpertBinding.ts` 的会话切换、`session.partnerExpert.set` 的持久化。验证重点包括多轮角色与方法持续生效、后续任务与排队运行、切换/移除、恢复和会话隔离。

2026-09-07 目录收敛：按用户要求，新选择仅展示产品管理、深度研究两个已完善的内置专家。其他七个占位预设退役，不再展示卡片；历史快照和用户副本继续保留。后续专家完成实际能力建设后再加入目录。

## 定义一个完整专家

在 `extensions/partner-library/manifest.json` 的 `experts` 中沿现有定义增加或更新：

- `prompt`：专业判断、适用边界、典型取舍；不要重复整个方法手册。
- `expertType`：`role` 或 `task`，仅影响目录。`category` 是领域，`starterTasks` 是可编辑草稿。
- `workflow.inputs`、`deliverables`、`qualityChecks`：各 1–8 项，每项最多 512 字符。描述用户能理解的输入、结果和检查标准。
- `workflow.connectorNeeds`：最多 5 项不同操作，操作来自 `read/search/append/createDocument/createBase`；用 `required` 和 `reason` 说明依赖。需求不授予权限，不填写账号、令牌或任意执行命令。只有任务确实依赖连接器时标记必需；本地资料也能完成的任务用可选。
- `skillRef`：需要方法时引用一个已有 Skill；没有合适的才添加。优先检查现有随包方法，以及 WorkBuddy / 豆包工作公开可复用包的原始来源。当前每个专家选择一个方法 Skill，用户可以关闭或切换。

产品管理和深度研究是配置到运行链路完整的基础样板，真实业务产出质量仍需评估。前者使用 `partner-product-management`，后者使用 `partner-deep-research`。方法源放 `resources/first-party-skills/<name>/SKILL.md`，登记 `resources/builtin-skills.sources.json`，运行 `npm run skills:update` 生成锁定快照，再运行 `npm run skills:check`。不要另建安装器或偷偷覆盖用户同名 Skill。

涉及行为、方法或交付定义变化时递增专家 `revision`。包含 workflow 或 retired 的包必须声明 `partnerExpertWorkflowsV1`，使用现有 host API v4；打包工具生成 UI 校验值。旧宿主会拒绝不认识的能力声明。

## 复用运行和交互

- `apps/desktop/electron/space-extensions/experts.ts` 管目录、用户副本和不可变会话快照。预设编辑生成用户副本；`workflow: null` 清空，省略则兼容旧编辑器并保留原值。
- `apps/desktop/electron/kodax/partner-profile.ts` 把专家与交付定义注入实际模型上下文，并把检查标准接入现有验证契约。它们是模型判断标准，不是假装已经验收的布尔标记。
- 沿现有 Skill 发现、`useSkill` 和运行注入链路，不另建专家执行器。连接器工具继续由宿主按实际会话、账号和范围提供；声明必需也不能绕过这些检查。
- `PartnerExpertDetails.tsx` 展示方法、资料、交付物和检查标准；插件编辑器提供同一套可编辑字段。
- `partnerConnectorGuidance.ts` 根据共享能力登记生成服务操作草稿；`PartnerCapabilityBar.tsx` 与连接器详情复用它。快捷操作插入输入框，用户仍可编辑，不自动发送。
- 读取结果、提案、创建成果继续使用共享资料与成果右栏。用户指定外部目的地时保留该目的地；能力缺失时说明补齐步骤，避免静默换成本地文件。

停用内置专家时保留原定义和 ID，并设置 `retired: true`。目录不再提供新选择，历史会话快照仍按原版本运行，用户副本继续可用；不要批量改写用户会话。

## 验证与证据

按实际改动选择现有公开接缝测试：schema 拒绝无效声明、目录与历史快照、复制/编辑/清空、Skill 开关、模型实际收到的方法与检查标准，以及当前会话连接器生成的草稿。可参考同目录的 `partner-expert.test.ts`、`experts.test.ts`、`partner-profile.test.ts` 和 `partner-connector-sdk.test.ts`。

PF008 的 `partner-expert-runtime.test.ts` 使用实际安装包定义和随包方法，经过真实 `session.partnerExpert.set`、Host 持久化/恢复和 SDK，检查连续任务、历史上下文、默认方法开关、显式 Skill 的单轮覆盖、切换/移除及其他会话隔离。`PartnerExpertChip.test.ts` 验证实际 Provider 和输入框的加载、持续使用、不可用与会话切换交互。新增专家复用这些生命周期样板，不为每个专家复制执行逻辑。

专家的样板验收至少有一个完整输入到交付的场景。控制模型和远端 transport 的自动测试用于证明接线、授权边界与交付路径；真实模型输出另按质量标准评估。不要把脚本模型返回的预设文本当成专业能力质量证明，也不要把 fixture 当成真实账号验证。

跨服务功能用已有服务组合验证。单次样板或局部修复不需要重复改连接器底层；只有真实能力缺口才进入连接器开发。完成适当回归、类型/lint、构建和实际 Electron 流程，保存可复核证据。Partner 的 `Completed / Local` 不代表 Space 集成或发布。

## 外部专家与 Skill 复用

2026-09-07 用户要求优先复用成熟材料。先检查本地已安装包、官方导出/下载和作者原始仓库，区别市场展示、可下载源码和可再分发许可；不要把归档站整库标注当作每个包的作者授权。

- 直接复用方法时，保留完整支持文件及 LICENSE，在 `builtin-skills.sources.json` 登记作者 repository、固定 Git ref、sourceSubdir 和许可 hash。运行现有同步器生成快照，不手写 lock。原有随包 Skill 不因扩专家而重复复制。
- 必要适配写入 `resources/builtin-skill-patches/`：处理平台专属工具、路径、必须调用却不存在的 Skill、未经证据支持的保证，以及与当前会话生命周期冲突的行为。保持专业方法本身可追溯，不把适配版伪称未修改原版。
- 专家包中的角色可按相同来源要求复用，但 WorkBuddy 的插件清单、Agent 工具和豆包的独立伙伴运行配置不能直接作为 Space 权限或执行器。把角色、方法和交付标准映射到现有 expert/workflow/skillRef，不另写一套运行引擎。
- 没有复用来源的领域再新增小范围自有方法。缺少源码或许可的市场内容先用于确定需求，不把显示出来的商品描述包装成“完整能力已移植”。
- 核验支持文件相对引用、实际 Skill 发现、完整方法进入模型上下文、原始任务保留、默认 Skill 开关与恢复；业务质量使用实际任务另测。记录上游版本、适配原因和能力边界，供下一次更新复查。

本轮发现 SDK 会将 `$50` / `$5` 解析为位置参数，外部方法中的普通金额应适配为 `USD 50` / `USD 5`。不要修改全局变量解析来迁就某一个包；用真实调用中的完整方法内容验证移植没有静默丢字。


2026-09-08 办公场景复用：新增流程与SOP、客户支持、资料综合与知识整理、工作汇报，当前目录为十二个专家（五岗位、七任务）。来源对照与下一批候选见 [PF010 调研](PF010-office-expert-research.md)。四个默认方法来自 Anthropic knowledge-work-plugins 的固定提交，通过现有 source/patch/lock 机制维护，不另建插件运行器。

办公方法验收关注原文模板是否暗含事实或权限：客户通知和跟进同样属于未来承诺；流程补料后重入点属于企业制度；任务项数未按成本/工作量加权时不能与预算消耗直接比较。真实输出暴露这些问题后，修改具体方法并保留失败与复测样例。市场角色挂载的技能数量不能替代 Space 自己的交付验收；不支持的格式、数据抓取和外部动作不能通过名称或提示词获得。

## 专家展示复用（PF011）

2026-09-08 PF013：目录扩展到16位（7岗位、9任务）。新增销售拜访顾问、招聘面试设计、新员工入职、演示文稿制作；前三个复用固定版本call-prep/interview-prep/onboarding，演示复用既有frontend-slides。四个储备头像已分配给这些实际专家，不再作为未用头像。HTML演示不承诺原生PPTX；入职计划不等于已开账号或已发邀请；面试评分必须有岗位相关回答证据。后续沿SDK恢复测试的expandedExpertTasks增加实际样板，不复制运行链路。

展示信息登记在 `extensions/partner-library/expert-presentation.json`：选择头像ID，填写三个能力标签和用户能理解的方法说明。素材位于 `apps/desktop/public/expert-avatars/`，16枚均已应用于实际专家，不能仅因有头像而增加空专家。未知和用户自建专家使用姓名首字回退。

卡片只打开详情；明确使用时才绑定专家。详情从真实 starterTasks 和 workflow 展示示例、输入、交付、检查与连接器需求，不编造使用量或案例。编辑、删除、原始提示词放入设置展开区。保留默认方法开关、浏览不修改会话和关闭恢复焦点。

宿主右栏共享展示元数据，独立插件通过 `readPartnerLibraryHtml` 嵌入头像，保持两文件归档与2MB上限。纯展示修改不递增专家行为 revision；行为和方法修改仍遵守不可变版本要求。验证离线头像、键盘、窄屏和既有选择/副本/删除/恢复流程。生成模式、完整提示和素材位置见 [PF011验收与素材](PF011-expert-presentation-validation.md)。
