# Windows daemon 冷启动到建连的耗时

2026-11-07，Windows x64，Node 22.23.1。调查对象是已加载 SDK 的客户端第一次执行 `createKodaXRuntime({ mode: 'daemon' })`，直至得到已连接的 Runtime。每个样本都启动新的客户端和 daemon。安装包下载、SDK 的首次 import、Electron 窗口绘制、读取 view 和历史正文均在此计时范围之外。操作系统文件缓存未清空。

## 回查引出问题的四轮原始记录

将[历史验收](../test-guides/ISSUE_237_0.1.47-alpha.4_REGRESSION_GUIDE.md)中的样本按各临时 home 的创建时间、构建分组和运行顺序对回当次的 daemon 日志。两个共同日志事件是 Windows Job 成员身份验证结束和 Host 开始发布服务。它们都由 daemon 记录，不受客户端轮询间隔影响。

| 中位耗时，ms | registry beta.2 | 当时验收的历史候选 B | 相差 |
| --- | ---: | ---: | ---: |
| 完整冷建连 | 2138 | 3466 | 1328 |
| Job 身份验证完毕至 Host 开始发布 | 131 | 1450 | 1319 |

原四次区间读数分别是发布包 149、113、132、130 ms，本地历史候选 1408、1436、1845、1464 ms。该区间包含数个操作。旧日志没有单独记录其中那条系统查询的耗时，不能把原批次的 1319 ms 全部算作查询时间。

## 对照如何构建

同源对照基于 KodaX `58671f8de` 加同一份未提交工作区快照。历史关闭组在临时副本中还原本次历史相关源码及打包规则。混合文件按改动块还原，保留工作模式锁定等并行工作。重新生成 REPL 历史投影，使用相同依赖、锁文件、构建工具和五个平台的 native 文件。只更改用户界面的 Space 改动未参与 SDK 计时。

| 组 | 与相邻组的区别 | CLI 字节 | CLI SHA-256 前 12 位 |
| --- | --- | ---: | --- |
| 历史关闭 | 当前快照移除本次历史功能 | 5,193,652 | `10ce9023e686` |
| 历史开启 | 当前快照，CLI 与已验收开发构建逐字节一致 | 5,192,179 | `b3cc44a28bed` |
| 只查开机时间 | 在历史开启组的原始查询中增加 `-Property LastBootUpTime` | 5,192,204 | `ef6cc9002aef` |

历史关闭组的 CLI 超出原生产预算 948 字节。隔离实验仅让构建器记录超限并保留产物，其余检查保持启用；历史开启组和查询实验组另行通过原生产构建。registry 原包用于对照上次报告，历史功能的归因使用同源的开启、关闭两组。

每次从固定快照复制会话到新的 `.kodax/sessions`。所有同源测量均使用 `profile: 'compare'`、`daemonStartupTimeoutMs: 20000` 与 `daemonOrphanExitMs: 300`。客户端在运行完成后断开，独立核对该 daemon 的退出记录。整个过程未运行模型或修改真实用户的会话及后台。

## 同源总耗时与各阶段

六个区组依次使用三种构建的六种排列，串行启动，每个区组各组测一次。无插桩完整建连中位数为发布包 1697 ms、历史关闭 2475 ms、历史开启 2570 ms。同一区组内“开启减关闭”依次为 +104、+308、−1、+316、−4、−288 ms，中位差 +51 ms。“开启减发布包”的配对中位差为 +972 ms。在该机器和样本中没有复现历史改动带来固定的秒级退化；无法据此排除较小的差别。

另做四个区组，将父子进程时间对齐。客户端使用启动进度回调，Host 使用自身的启动日志，临时 Node 观察脚本记录 daemon 进程入口及同步子进程调用耗时。探针按原样调用系统程序。下表各行独立取中位数，不能相加得到总数。

| --- | ---: | ---: | ---: |

| 拉起 Windows 监管进程至进入 daemon Node 进程 | 399 | 395 | 388 |

## 为什么有这条系统查询

11 月 6 日的 SDK 提交 `587f9a9ba` 为异常退出恢复增加了 Windows 所有者证据。监管进程验证 Job 成员身份后，daemon 在发布所有者记录之前执行 `readWindowsSandboxBootIdentity()`。这会启动 PowerShell，用 `Get-CimInstance Win32_OperatingSystem` 读取系统启动时间，将 UTC ticks 写入所有者记录。恢复时可用该值区分不同系统启动周期。正常情况下结果缓存在当前进程，每个新 daemon 需重新取得。该调用早于历史功能，发布的 beta.2 尚未包含它。

在本机 Windows PowerShell 中单独交错运行六对查询，在同一轮系统启动中比较两种请求的完整 ticks。两者每次返回相同值。取整个对象时查询本身的中位数为 764 ms，含启动 PowerShell 为 913 ms。只取 `LastBootUpTime` 时分别为 65 ms 和 222 ms。只查属性的实验保持相同 CIM 类、身份验证、UTC 转换、超时及失败处理。

## 是否值得优化

在真实 daemon 启动流程中，只改变一处查询，再与历史开启组交错运行六对。完整冷建连的中位数从 **2516 ms 降到 1872 ms**。六组分别节省 649、631、597、565、678、704 ms，配对中位节省 **640 ms**。所有同源样本的 `daemon.lock` 都写入了相同的有效开机身份。另用空 sessions 目录复测，原查询的当前包为 2600、2619 ms，发布包为 1783、1870 ms，额外延迟无需打开旧会话即可出现。

建议保留历史契约，在 SDK 的 Windows 开机身份读取器中单独采用窄查询。这个改法仍需系统启动周期证明，沿用现有 5 秒超时、失败处理及进程内缓存。实验覆盖本机 Windows PowerShell 和同一次系统启动，生产合入时应补验 PowerShell 7、取值失败和重启后的恢复路径。本轮只在独立临时构建验证这一行查询，未改开发或发布包。

可复核 46 次串行测量的[逐次计时 CSV](windows-daemon-cold-connect-2026-11-07.csv)。`plain` 为无插桩开关对照及额外的空目录样本，`trace` 为探针组，`option` 为无插桩的查询选项对照。各事件列记录相对于 SDK 调用起点的毫秒数，`boot_query_duration_ms` 是查询自身耗时。每一行都观察到该隔离 daemon 的退出记录。
