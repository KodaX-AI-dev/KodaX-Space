# F144 票 1：真实链路基线与决策门

> 2026-11-10。机器可读数据：[f144-ticket1-baseline.json](f144-ticket1-baseline.json)（含每次前插/后接的逐步拆分）。

## 决策门结论

**DOM/布局为主 → 进入第二段（窗口化）。** IPC/正文解析不是瓶颈，不需要先收窄预取。

依据（以 10k Coder 为主，Partner 10k 同形，30k 进一步放大）：

1. **主进程 + SDK 读取 + 解析是常数且很小。** 纯 IPC 探针（不经 React）每页 p50 约 16–18 ms、约 160 KB、约 180 条；其中主进程 handler 15 ms、SDK `readHistory`（daemon IPC + KodaX 解析）12 ms、Space 投影 0 ms。1k / 10k / 30k 三个规模下这几个数基本不变。
2. **渲染进程开销随挂载行数线性增长，且占绝对多数。** 10k 前插单步 p50 1671 ms / max 3887 ms，其中 commit（React render + commit + layout effect，含锚点恢复的强制布局）p50 774 ms、paint（下一帧 style/layout/paint）p50 575 ms。前 5 页平均 218 ms，后 5 页平均 3622 ms；commit 从 153 ms 涨到 1362 ms。30k 前插到 24k 行时，后 5 页平均 13.8 s，commit 从 136 ms 涨到 3552 ms。主进程那 ~15 ms 不到 1%。
3. **渲染侧记录的 “ipc” 也随行数增长**（1k p50 22 ms，10k p50 302 ms / max 729 ms，30k p50 1017 ms / max 3315 ms），但同时间主进程 handler 只有 15–24 ms。多出来的时间是渲染主线程忙：`phase: 'loading'` 那次 publish 要在 invoke 发出前先把整列重渲一遍，回复又在忙碌的线程上排队。所以这也是 DOM/React 开销，不是 IPC。
4. **长滚动卡顿。** 约 9.9k 挂载行时，每帧 1500 px 的程序化滚动 p50 606 ms、p95 707 ms，120 帧全部超过 50 ms，共 119 个 long task、合计 71.8 s。约 24k 行时 p50 2986 ms，125 个 long task 合计 356 s。1.1k 行时 p50 33 ms，空闲帧 16.7 ms。
5. **堆和卸载也随行数增长。** 每个挂载行约 31–32 KB 堆（4206 行 149 MB，9872 行 324 MB，30k 语料 24255 行 753 MB）。jump-to-bottom 从 1110 行要 203 ms，从 9872 行要 1027 ms，从 24255 行要 4910 ms。

所以第二段的收益点是减少挂载行数，即窗口化。附带的次要发现：冷打开时 newest 页的主进程 view 读取随文件大小增长，留作冷启动路径的独立观察（见“发现”第 3 条），不影响本结论。

## 语料与方法

语料由 `tests/e2e/helpers/perfCorpus.ts` 按固定 seed 生成，通过 SDK 公共 `createSessionManager` 写入。正文是混合高度的 markdown / 代码 / 列表，并带有工具轮。没有使用 ipcMain mock：所有数字都走真实的 SDK 读取 → main `session.history` → 渲染安装链路。

| 语料        | 轮数  | 消息数 / 文件大小 | 全量行数（约） | 说明                                                           |
| ----------- | ----- | ----------------- | -------------- | -------------------------------------------------------------- |
| coder-1k    | 420   | 1020 / 1.0 MB     | 1.1k           |                                                                |
| coder-10k   | 3800  | 9130 / 8.6 MB     | 9.9k           |                                                                |
| coder-30k   | 11400 | 27300 / 25.5 MB   | 30k            |                                                                |
| coder-giant | 120   | 282 / 1.6 MB      | 300            | 单条 1,000,000 字符正文（渲染 905k 字符）+ 单轮 300 个工具调用 |
| partner-10k | 3800  | 9170 / 8.7 MB     | 9.9k           | SDK `tag: 'partner'`，与 Coder 走同一 productItems 路径        |

每个语料单独启动一个 Space 实例，依次跑下面几段：

1. **打开**：在侧栏点击 Session，计时到最新回答绘出（首绘）。记录挂载行数、强制 GC 后的堆和空闲帧。
2. **前插**：点 “Browse history messages”，然后反复执行：scrollTop 置 0 → 滚轮 −120 → 等到对应 `kodax.history.paint` → 沉降 40 帧 → 测锚点漂移。直到最旧一条出现，或耗尽 75 min 预算。每 25 页采一次堆。之后测长滚动（每帧 1500 px，最多 120 帧）和 jump-to-bottom。
3. **后接**：`page.reload()` 后重新打开 Session，用 Ctrl+F 搜 `PERF_Q_0` 定位到最旧窗口（`around`），然后向较新方向翻页。直到最新一条，或达到上限（10k / 30k 为 25 页）。
4. **IPC 探针**：直接调用 `session.history`，从最新页向旧方向走 30 页，不经 React；同时读取主进程诊断日志里的 handler / view / sdkRead / project 时间。

拆分来自 `apps/desktop/renderer/src/lib/historyLoadDiagnostics.ts` 的 `performance.measure`，以及主进程的 `session-history` debug 日志：

| 段      | 含义                                                                                       |
| ------- | ------------------------------------------------------------------------------------------ |
| ipc     | 渲染侧从发起到收到回复                                                                     |
| install | 写入 store                                                                                 |
| commit  | 到 publish 后的 microtask：React render + commit + layout effect，含锚点恢复引起的强制布局 |
| layout  | 之后单独强制一次布局（因为大部分已在 commit 内完成，所以约 0.2 ms）                        |
| paint   | rAF + setTimeout，即下一帧的 style/layout/paint                                            |

## 发现（与决策门无关，需要单独跟进）

1. **冷打开 30k Session 后的第一个较旧页返回 `data_changed`。** 三次独立运行都能复现：冷打开后点 Browse，再上滚，界面显示 “Saved history changed while you were reading”，并停在 157 行。这次请求在主进程没有留下 `page_read` 记录，说明 SDK `readHistory(cursor)` 在投影之前就以 resync / data_changed 拒绝了冷打开时拿到的游标。点 “Return to newest messages” 重新读取 newest 之后，翻页恢复正常（30k 的前插数字就是恢复后测的，结果 JSON 里记为 `staleFirstAttempt`）。热路径也不受影响：重载后的后接，以及 30 页 IPC 探针都正常。1k 和 10k 没有出现。冷打开 newest 时，主进程 view 读取（`readSessionProductView`，首次观察）耗时 1.9 s，而文件有 25.5 MB。推测这次首次观察在 newest 修订号被捕获之后，又推进了 Session 元数据。尚未定位到根因。
2. **从 `around` 窗口向较新方向后接时，锚点漂移约 54 px。** 1k 的 p50 为 53.6 px；10k / 30k 最大 133 / 55 px。滚轮增量从 −600 改成 −120 结果不变，所以这是真实的布局位移，不是滚轮惯性。前插的漂移始终 ≤ 0.4 px。根因未查。
3. **冷打开 newest 的成本随文件大小增长。** 渲染侧 ipc 为 494 / 1377 / 2326 ms（1 / 8.6 / 25.5 MB）；其中主进程 view 为 178 / 618 / 1875 ms，SDK 读取为 298 / 684 / 271 ms。热重开时为 173–224 ms。这属于冷启动 / 首次观察路径，不在逐页加载上，也不改变决策门结论。

## 口径与局限

- commit 段包含 layout effect，以及锚点恢复引起的强制布局，所以单独的 layout 段只有约 0.2 ms。“DOM/布局” 指的是 commit + paint 合计。
- 滚动是程序化的（rAF 驱动，每帧 1500 px），不是真实的触控板惯性。测量在隔离桌面上进行。
- 每个语料只跑了一次。10k 与 partner-10k 的形状一致，可以互相印证；数值抖动未量化。
- 前插单步的墙钟时间远大于表中数字：10k 末段每步约 16 s，因为 40 个沉降帧每帧约 300 ms。
- 后接在 10k / 30k 上限 25 页，所以后接数字对应约 4.1k 挂载行。
- 30k 前插在 75 min 预算处停止（148 页，24255 行），没有到最旧一条。此时单步 p50 已达 5 s、末段约 14 s，跑满 30k 行不会改变结论。
