# KodaX Space 任务伴侣：有趣、有用、安静

2026-10-16 · 产品设计提案 · 待讨论，未实施

2026-10-17 素材方向更新：用户允许舍弃旧两套小狗，改为一套统一的新角色与动作集。新造型与关键姿态见[新小狗素材设计](companion-dog-v3.md)；本次仍处于设计评审，正式产品尚未替换。

本轮只设计角色、位置、交互与行为边界。正式产品代码、现有宠物、Quick Ask、任务执行、设置与通知均未因本提案改变。本文不是已验收的功能规格，也不代表 SDK 旁路能力已经集成。

## 1. 推荐方向

让原来的小狗成为「任务伴侣」：平时安静陪伴，用一句话帮助用户理解当前工作；用户点开时，可以了解进展、追问已发生的事情、找到需要处理的决策。它与主执行 Agent 共用任务事实，但拥有独立的旁聊。

三个目标按顺序约束设计：

1. **有价值**：帮助用户回答“做到了哪里、现在在做什么、有没有需要我处理的事”。
2. **不打扰**：普通进展不抢焦点、不展开侧栏、不覆盖代码、不改变主任务。
3. **有趣味**：用小动作、轻语气和及时回应建立陪伴感；趣味附着在真实事件上。

这里的「独立角色」是产品交互身份。它不需要常驻运行第二个有工具权限的 Agent。状态展示可以完全本地完成，旁聊按需调用模型。

## 2. 参考了什么，采用什么

Claude Code `/btw` 的价值在于：基于已有上下文回答旁路问题，终端旁问没有工具权限，主任务可以继续运行，旁问不写入主会话。Codex 官方也提供 `/side`，其旁聊与主聊天 transcript 分离，桌面命令说明明确支持不中断主聊天。不同产品的工具权限与保存规则不能相互套用。[Claude 官方说明](https://code.claude.com/docs/en/interactive-mode#side-questions-with-btw)、[Codex 官方说明](https://learn.chatgpt.com/docs/developer-commands#start-a-side-chat-with-side)。

本方案采用“执行与解释分开”，并针对 Space 增加有范围标识的多项目状态汇总。主动更新按用户当前任务与注意力择时、允许关闭，也保留无需焦点转移的文字状态；这些方向参考 [Microsoft HAX](https://www.microsoft.com/en-us/haxtoolkit/guideline/time-services-based-on-context/)、[Google PAIR](https://pair.withgoogle.com/guidebook-v2/chapter/feedback-controls/) 和 [W3C 状态消息说明](https://www.w3.org/WAI/WCAG21/Understanding/status-messages.html#intent)。具体位置、时长与默认值是本产品建议，尚无用户实验结论。

完整事实、证据边界和未证实项见[调研笔记](../research/task-companion-interactions-2026-10-16.md)。

## 3. 位置：推荐项目栏底部的固定座位

| 位置               | 适合的角色                   | 收益与代价                                                         | 建议             |
| ------------------ | ---------------------------- | ------------------------------------------------------------------ | ---------------- |
| 现有输入框上沿     | 当前任务的小伙伴             | 保留原来的亲近感；可用空间小，容易与附件、提示和发送状态争夺注意力 | 保留为位置选项   |
| 项目栏底部         | 能看当前任务与并行项目的伴侣 | 稳定、可发现、不会遮正文；项目栏收起时需要替代入口                 | 推荐常驻位置     |
| 工作区标题/状态栏  | 紧凑状态入口                 | 专注或窄窗时仍可达；宠物只能较小展示                               | 推荐折叠形态     |
| 右侧详情栏常驻     | 深入解释与问答               | 阅读空间充分，但永久占据右栏会挤压任务详情                         | 仅用户打开时使用 |
| 任意漂浮或跟随光标 | 娱乐性宠物                   | 位置不可预测，容易遮挡内容和操作目标                               | 首版不采用       |

推荐把项目栏现有底部区域整合为一条伴侣座位，而不是再叠一张卡片。设置齿轮保持独立可达。宠物约 32–40 px，点击区域至少 44 px；旁边容纳短状态和“1 项待处理”之类的文字。尺寸是布局验证起点，不是冻结规格。

常驻状态最多两行，例如：

> Atlas Web · 正在验证登录流程  
> 另有 2 个任务运行，1 项待处理

第一行跟随当前主工作区，第二行只汇总本窗口已获访问权限的任务元数据。没有任务时只显示「任务伴侣」，不编造建议来填满空间。项目栏收起或进入专注时，同一入口折叠至工作区标题区域；全窗口只有一处播放宠物动画。

原输入栏位置仍可选择。正式迁移前需要确认默认位置与顶栏爪印动作，见第 14 节。

## 4. 三层交互，逐步展开

### 安静陪伴

默认只显示宠物与一句状态。任务状态可以及时变化，但每个工具调用、token 和循环次数都不成为新消息。悬停或键盘聚焦可查看完整状态，不触发模型请求。

### 值得知道的进展

有明显里程碑时，伴侣座位显示一条短说明，例如「登录模块已完成，正在运行回归」。相同任务短时间内的变化合并到这一处。无需浮出大气泡、Toast 或新聊天消息；用户正在输入、选择文字、拖动或阅读历史时，普通说明延后。

说明及依据可在伴侣面板回看。被下一条替换不代表记录丢失；阶段性变化不累计成红色未读数字。只有确实需要用户处理的事项显示待处理数。

### 用户主动旁聊

点击伴侣打开右侧「伴侣」工作面，复用现有右栏的空间。主正文、草稿、运行和原右栏状态保持；原 Run、Plan、Agents、Workflow、Changes、Sources、Artifacts、Context 等入口继续可达，关闭伴侣恢复原详情。

不增加第四个永久栏。窄窗可由用户主动打开覆盖式面板；专注模式仅在用户点击入口后打开伴侣，关闭后恢复专注。自动进展始终不能执行这些打开动作。

面板从上到下：

- **范围**：项目 / 会话，显示旁聊只解释已有信息；提供切换任务入口。
- **最新简报**：已确认、进行中、需要你；有依据时再显示下一步。
- **旁聊**：用户问答和可展开的简报记录，共用一条轻量阅读流。
- **输入**：占位文案「问问这个任务的进展、原因或结果…」。停止按钮只取消旁聊请求。

首屏只露出三个示例问题：「现在做到哪了？」「有什么需要我决定？」「刚才发生了什么？」进入对话后收起示例，不把面板做成能力菜单。

## 5. 什么值得主动说

“每过几轮”可以触发内部检查，不能自动推出“应该发一条消息”。用户得到的应当是新信息，而不是报时。

| 情况                                 | 可见反馈                             | 默认时机                            |
| ------------------------------------ | ------------------------------------ | ----------------------------------- |
| 任务开始                             | 一句正在处理的状态                   | 更新原位置，不另发欢迎消息          |
| 明确阶段变化、重要产物可查看         | 一句阶段说明，面板保留详情           | 合并后在合适空隙显示                |
| 明确完成或失败                       | 一句结果 + 查看/处理入口             | 沿用现有完成/失败通知策略，避免重复 |
| 等待用户答复、审批或预算决定         | 持续的“需要你处理”状态               | 立即更新状态，跳转原答复/审批界面   |
| 仅循环次数增加、零碎读写、没有新事实 | 不新增简报                           | 保持现有状态                        |
| 长时间没有新事件                     | 必要时显示“尚未收到新进展”及更新时间 | 超时本身不证明卡住、失败或快完成    |
| 用户离开后返回，期间有重要变化       | 一条“你离开期间”的合并简报           | 前台恢复后择时，不逐条补播          |
| 其他项目有普通进展                   | 全局计数更新，详情留在各自任务       | 不覆盖当前任务的一句话              |

普通说明的初始调优起点：同一任务约 60–120 秒内合并，全窗口同一时刻最多呈现一条。若 SDK 提供有明确语义的阶段事件，优先事件；累计 3–5 个执行循环仅作检查是否已有值得总结的变化。以上数值是试验起点，需用真实任务回放调整；用户无需配置这些内部参数。

需要处理的状态不受普通简报冷却限制，但也不通过自动展开伴侣、系统声音或焦点跳转表达。已有原生通知的开关与发送规则继续负责系统级提醒。

主 Agent 刚刚给出同样的可见进度时，伴侣更新状态与索引即可，不再生成同义内容。去重以任务、Run 和语义事件边界为依据，不能仅按文本相似度合并不同事实。

## 6. 趣味性从动作和时机产生

采用一套统一的新小狗角色，为状态设计完整关键姿态和后续连续动作帧。旧两套不再作为必须保留的样式；不预设引入骨骼或 WebGL 运行时。当前已生成的九种关键姿态是素材设计稿，尚非动画成品。

| 时刻              | 小狗表现                 | 信息含义                             |
| ----------------- | ------------------------ | ------------------------------------ |
| 无任务或安静等待  | 轻微呼吸、偶尔坐下或打盹 | 不反复邀请用户聊天                   |
| 主任务执行        | 专注的姿态，间歇小动作   | 正在工作，完成程度仍看文字           |
| 用户主动点击/悬停 | 一次抬头或轻摇尾巴       | 回应用户，随后安静                   |
| 重要阶段完成      | 一次短动作，随后恢复原位 | 有一项可查看的新进展                 |
| 任务结束          | 一次克制的庆祝           | “本轮结束”与“验证通过”分别用文字表达 |
| 等待决策或错误    | 看向状态文字、安静停留   | 提醒查看，不夸张跳跃或反复催促       |

动画只在自己的小座位内活动，不穿过项目名称、不追逐光标、不在代码上巡游。用户输入只产生低频回应，不能每敲一个字就触发动作。没有积分、签到、喂养、随机奖励或需要照料的机制。

语气是友善、简短、可靠。可以说「回来啦，Atlas Web 有一项结果待看」，避免反复自我介绍、无意义鼓励或把用户称作主人。事实内容优先，轻松语气只出现于适合的开头或结尾。

## 7. 旁聊能回答什么，如何回到执行

旁聊适合：解释已读代码、复述已确认决策、讲清工具为何运行、总结已有结果、指出当前需要用户处理的事项。它只获得当前选定任务的有界快照与旁聊历史；不默认读取其他项目正文、隐藏思考、任意本地文件或未返回的工具输出。

主聊天材料通过 SDK 的公开 view/history 接口取得，不能从原始事件重新拼一份 assistant 回复。未完成的流式内容只标记为生成中，不据半句话认定任务结果；最近消息过多时明确提示本次只参考了哪些片段。

每个答案显示其任务范围和数据截至时间。下一次提问获取新的可用快照；同一个答案生成期间不拼入不断变化的主任务正文。若主任务已更新，可显示「主任务已有更新」并让用户刷新。

模型、Provider 与上下文范围在发起这次提问时绑定；用户随后切换项目或模型，不改变在途请求。主任务快照不等于主模型全部隐含上下文，不能宣称伴侣“知道它心里正在想什么”。

询问当前快照无法回答的问题时，明确说明缺失的信息。例如：

> 目前能确认的是回归命令仍在运行，尚未收到退出结果；这些信息不能判断它是否卡住。可以查看运行详情，或把进一步排查的要求交给主任务。

如果用户说“帮我把它改掉”，伴侣生成一段可审阅的主任务草稿，并提供「加入主任务草稿」。它不直接发送、不停止当前 Run、不替用户选立即打断或排队。发送动作继续使用现有主输入框和执行规则；有旧草稿时保留旧内容，不能静默覆盖。

审批只提供跳转原审批卡的入口，不能让旁聊中的“好”“继续”被当成授权。主任务失败时，旁聊失败与主任务失败也分别呈现。

## 8. 多项目并行：一个形象，范围明确

全窗口用一个伴侣形象，任务简报与旁聊按项目、会话隔离。全局概览只汇总任务名、状态、待处理数和更新时间；进入具体任务再看内容与证据。

例如三个项目同时进行：

- Atlas Web：验证中。
- KodaX Space：等待一项产品决策。
- Docs Site：生成完成，结果待看。

当前主工作区仍是 Atlas Web。伴侣可以说明「其他项目有 1 项需要处理」，点击后让用户选择目标；不能自动跳项目或把另一个项目的进展冒充当前任务。

伴侣面板打开后绑定当时的会话。用户切换主项目时，已打开旁聊保持原范围，标题明确显示它属于哪个任务，并提供「切到当前任务」。输入中的问题和已开始的答案继续归原任务，不在半途改绑；各会话草稿分别保留。

未知、断线与恢复中的状态明确标记为未确认，并显示最后更新时间。后台任务的真实快照不足时，只显示已知状态，不为给宠物增加能力而逐一加载所有历史。

## 9. 简报的真实性

一条完整简报回答三件事：**已确认什么、正在做什么、需要用户做什么**。没有证据的项可以省略；下一步如果来自推测，要标为建议，不能冒充主任务已作出的计划。

示例均为设计示例，不是真实运行结果：

> Atlas Web · 登录重构  
> 已确认：登录表单与错误提示已经修改。  
> 正在做：回归命令尚未结束。  
> 需要你：暂无。  
> 依据：2 项任务更新、1 条运行状态 · 截至 15:32

“计划项标记完成”“命令成功结束”“任务执行结束”“测试通过”“用户目标达成”不是同一事实。只有确实取得相应证据时，才能使用对应措辞。不展示虚构百分比、剩余时间，不用宠物表情代替最终验证。

证据链接打开已存在的消息、工具结果、计划或产物。自动简报不写入主 SDK 聊天，不重建第二份 assistant 正文。模型生成的解释需标明是基于这些材料的概括，引用必须对应快照中实际存在的项目。

## 10. 默认与控制：先让安静成为基线

主动程度只有三个用户可理解的档位，不增加每轮/秒数等设置：

| 档位                 | 行为                                           | 费用边界                                           |
| -------------------- | ---------------------------------------------- | -------------------------------------------------- |
| 安静陪伴             | 宠物与原地状态；用户点开再看简报和问答         | 状态无需模型；主动询问才产生模型请求               |
| 关键节点（建议默认） | 重要变化的一句话 + 按需旁聊                    | 默认优先已有进度与本地模板，不新增定时模型请求     |
| 主动简报             | 对有明显变化的长任务，合并生成更自然的阶段说明 | 单独启用；展示使用的 Provider/模型、额外消耗与限制 |

宠物是否显示与主动程度分开，统一新角色后不再提供旧两套样式轮换。关闭宠物形象后可保留文字伴侣入口；关闭主动简报后仍保留原审批、错误与任务状态。单任务提供「本任务保持安静」，不要求用户改全局偏好。

旧用户升级时沿用宠物显示/关闭、位置与通知偏好；原版或精灵版均迁为新统一角色，原关闭值继续关闭。不静默开启新的付费自动摘要。新用户的推荐位置与关键节点默认值，需在方案确认后才成为实现决策。

中英文跟随现有系统/个人语言设置。模板与控件即时切换；已生成的旁聊和证据保留原文，新答案使用当前界面语言，用户明确要求其他语言时遵从用户。

## 11. 动效与性能

沿用已有三档视觉效果，不为宠物新增一套性能档位：

- **极简**：静态宠物与完整文字状态，功能不减少。
- **均衡**：局部玻璃、短状态变化与用户触发的小动作；没有持续吸睛的巡游。
- **全特效**：允许低频待机与更多姿态，范围仍限定在小座位。

系统减少动画优先于视觉档位。失焦、后台、被设置页遮住或入口不可见时暂停装饰动画；恢复后不补播错过的动作。读屏获取经过合并的文字状态，不能每帧或每个 token 播报；普通状态使用无需抢焦点的礼貌播报。

状态订阅复用既有任务投影，事件增量驱动，禁止按固定间隔扫描所有聊天全文。模型问答只在主进程经已有凭据体系执行；自动摘要可合并、取消、设输入/输出上限。共享 Provider 触发限流或主任务重试时，自动摘要让路，不能抢占主任务的重试预算。

自动模型摘要采用全窗口最多一个在途请求的初始策略，排队时同一任务只保留最新快照。任务已停止、事实已过期、用户已静音时丢弃未发起请求；已产生的实际用量仍如实计费展示。手动旁聊优先于自动摘要，关闭自动摘要不取消用户主动发起的问题。

“不打断”包含不发送主任务消息、不取消它、不抢焦点，以及尽量减少共享计算/网络竞争；不能承诺额外模型请求永远没有资源影响。手动旁聊与主任务仍会共享可能受限的 Provider，界面应如实表达等待。

## 13. 旁聊保存与异常行为

建议旁聊按任务在本机独立保存，支持清空，随主任务删除；不参与主任务历史、搜索排序和最近消息时间。界面明确说明“旁聊单独保存”，不沿用其他产品的“临时”承诺。

自动简报保存有界的最近记录与证据引用，连续工具过程合并成阶段；不另存完整日志副本。具体数量和保留期在实现规格中结合现有存储约定确定，不作为新设置暴露。用户可把重要内容加入主任务草稿后主动发送。

| 边界情况                       | 产品行为                                                                     |
| ------------------------------ | ---------------------------------------------------------------------------- |
| 用户切项目时旁聊尚未返回       | 答案回到原任务旁聊，标明原项目，不写进新项目                                 |
| 主任务开始新 Run、取消或失败   | 未展示的旧自动摘要作废或明确标旧；旁聊保留其快照时间，不冒充当前状态         |
| 证据已删除、归档或无法访问     | 显示证据不可用，不让模型补造依据                                             |
| 模型失败、超时、无凭据或被限流 | 真实状态与手动跳转继续可用；旁聊说明失败，自动简报停止重试风暴               |
| 用户关闭面板或隐藏宠物         | 不停止主任务、不删除旁聊、不撤销审批；正在手动生成的旁聊可由明确停止按钮取消 |
| 用户清空旁聊                   | 清理旁聊与其草稿，不删除主任务记录                                           |
| 主任务回复已包含完整阶段总结   | 旁聊可以引用该总结，默认不另发近义汇报                                       |

任务材料中的文本只是待解释的数据，不能改变旁聊的项目范围、工具权限与执行边界。正文快照不包含凭据、隐藏思考或原始调试转储；主进程负责范围与凭据校验。

## 14. 需要与用户对齐的交互变化

旧两套宠物素材与样式入口已获用户替换授权，正式集成时可淘汰；任务、工作流、显示/关闭等能力继续保留。以下其他交互变化需在完整工作区原型中确认，再实施：

1. **宠物从输入栏移至项目栏底部作为推荐位置**；原输入栏位置继续可选，旧用户不自动迁移。
2. **新伴侣模式里，点击宠物打开旁聊**；原装饰模式保持原行为。
3. **顶栏爪印的主动作建议变为打开伴侣**；统一角色后旧两套样式轮换可以移除，显示/关闭保留在伴侣菜单/偏好。打开伴侣的入口位置与行为待原型确认。
4. **右栏新增伴侣工作面**；原详情入口与状态保留，不能以伴侣替代原 Run/Plan 等功能。
5. **新增自动汇报与本机旁聊保存**；自动模型摘要单独开启并显示额外成本，不能暗中使用主模型定时发请求。

以上是待讨论的建议，不把“需要确认”理解为阻止本轮设计继续，也不据此登记功能已开始开发。

## 15. 完整使用场景与验证标准

### 场景 A：安静写代码

主 Agent 在 Atlas Web 跑回归，用户正在编辑另一处文件。小狗保持工作姿态，原地状态更新；主 Agent 已说过的进度不重复。期间没有新事实，伴侣不发“仍在努力”。用户暂停操作后，重要阶段变化用一句话呈现。全过程零焦点转移、零自动开栏。

### 场景 B：随口了解，不改变任务

用户点开伴侣问“为什么运行这个命令？”答复引用当前任务已经记录的工具调用和上下文。主任务继续输出。用户说“顺便改一下”，伴侣给出可审阅草稿，用户回到主输入框决定何时发送。旁聊没有悄悄成为一条执行指令。

### 场景 C：三个项目并行

Atlas Web 仍在运行；KodaX Space 等产品决策；Docs Site 已完成。全局座位显示待处理数量，具体摘要带项目标签。用户点击 KodaX Space 的待处理事项进入原决策位置，其他任务继续运行；不因任务结束而自动切项目。

### 场景 D：用户回来与异常

用户离开期间一个阶段完成、一个任务失败。回来只呈现合并概览，失败保留原处理入口。若 Runtime 断线，伴侣显示“状态暂未确认，最后更新于…”；宠物不庆祝，也不把长时间没有事件称为卡死。

### 场景 E：主动程度可控

用户开启“主动简报”，看到一次有依据的阶段归纳及单独消耗；之后选择“本任务保持安静”。该任务的主动说明停止，原任务、审批和错误通知继续正常工作。关掉形象后，同样能通过文字入口问进度。

用这些场景做可用性验证，先看以下目标而不是宠物点击率：

- 用户能否在约 10 秒内说出当前在做什么、是否需要自己处理；此为验证目标，不是已测结果。
- 普通主动更新导致的焦点转移、自动开栏、主任务消息注入均为 0。
- 跨项目答案归属错误、失效摘要冒充当前进度、取消/失败误报完成均为 0。
- 用户能否找到静音、切换范围、查看证据、加入主任务草稿和返回原右栏。
- 模板状态的额外模型请求为 0；自动模型摘要的次数、tokens、失败与等待可独立查看。
- 对照无伴侣的真实任务，检查工作打断、理解速度与主任务吞吐，评估趣味是否带来实际收益。
- 深浅主题、三档视觉、减少动画、窄窗、专注、设置往返、重载与双项目运行不回退。

## 16. 建议推进顺序

当前只完成调研与产品方案。下一步应是完整工作区内的交互原型：安静运行、旁聊、多项目待处理、用户返回、失败、设置往返六组状态；沿用本次融合的视觉语言，不重新做三套品牌主题。

原型确认后再形成正式规格与测试边界。实现建议先连通本地可信状态和手动旁聊，再评估可选自动模型简报。这个先后顺序用于验证价值和成本，不能据此删掉本提案讨论的能力。
