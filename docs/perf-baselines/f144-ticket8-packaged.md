# F144 票 8：Windows 打包实测（窗口化默认开启）

> 2026-11-11。机器可读数据：[f144-ticket8-packaged.json](f144-ticket8-packaged.json)。对照：[票 1 基线（整列挂载）](f144-ticket1-baseline.md)、[票 4 基线（gate 开，源码运行）](f144-ticket4-windowed.md)。

## 结论

- **验收标准在 Windows 打包产物上全部满足。** 5 个语料在打开、前插、后接、搜索定位、跳转全程最多挂载 20 行，远低于 500 的验收线。前插漂移 ≤0.4 px，后接 ≤1.2 px（≤2 px）。没有 stale 首次失败、页面错误或控制台告警。
- **长滚动不再随已加载量变慢。** 5 个语料的长滚动帧 p50/p95 都是 16.7/16.8 ms（60 Hz 一帧），>50 ms 帧和 long task 都是 0。票 4 时 10k 为 457 ms、30k 为 3632 ms，瓶颈 query rail 已在票 6 改为有界渲染。
- **30k 第一次完整加载到最早一页。** 181 页（32,773 条）用时 3.6 min。票 4 时同一流程在 75 min 预算处停止（177 页）。前插 total p50 为 64.9 ms（票 4 为 2035 ms），jump-to-bottom 为 61 ms（票 4 为 3664 ms）。
- **打包产物与源码运行一致。** 10k 的前插 p50 45 ms、后接 43 ms、jump-to-bottom 61 ms、长滚动 16.7 ms，与票 6 源码实测（45 / 40.5 / 61 / 16.7 ms）相同。
- **macOS/Linux 尚无本地数据。** 发布流程的打包验收（`release.yml` acceptance，四个平台）新增一步：对打包产物跑 coder-10k，挂载行数 >500 即验收失败，结果 JSON 随验收证据上传。下一次 `workflow_dispatch` 或 tag 发布即产出 macOS x64/arm64 与 Linux 的数据；这一步尚未在 CI 上实际运行过。

## 环境与方法

机器与票 1/票 4 相同（Intel Core Ultra 7 270K Plus、24 核、63 GB、Windows 11 26300、Electron 42.5.0 / Chrome 148、1280×900 隔离桌面），同一 seed 语料、同一流程。产品为 `npm run build:win` 产出的 `out/win-unpacked/KodaX Space.exe`，代码为 `0d480355` 加票 8 改动（即加入本文件的提交）；窗口化已是唯一路径，不再有 gate。结果写入 `artifacts/perf-baselines/f144/<corpus>-packaged.json`，`environment.packaged` 为 `true`。

性能 spec 现在也是验收：页面错误、模型请求、全程挂载行数 >500 任一出现即失败。“行数”指挂载的 `conversation-render-row`。

## 读法

- 打开时行数很小（Partner 为 1）是因为 overscan 只有上下各一屏，newest 附近的行很高；这是预期行为。
- 30k 前插 max 770 ms 只出现在第一页：冷打开后第一次读较早页，渲染侧 ipc 750 ms，其余 180 页 ipc p95 为 27 ms。冷打开首绘随文件大小增长（30k 2312 ms）也是同一冷启动路径（Issue 244），与窗口化无关。
- 堆随已加载条目增长（30k 约 1.4 KB/条），这是已加载数据，不是 DOM；jump-to-bottom 后回落。
- 搜索定位 around 的成本主要是 ipc（30k 282 ms / total 314 ms）。
