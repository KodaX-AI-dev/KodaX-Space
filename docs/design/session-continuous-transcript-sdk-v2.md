# 长 Run 与长会话的连续阅读：基于 SDK v2 的 Space 阅读模型

状态：设计稿，2026-11-25。依赖 KodaX `KodaX-next-dev` 的 v2 Host 协议（尚未发布）和 Space 切换到 v2（SDK 计划中的 M1c）。本文不改变当前发布行为。

## 1. 问题

一个 session 只跑了一轮，界面上只有一行“运行了 111 个命令”，顶部却出现“浏览历史消息”，用户自己的提问也看不到了。

复现样本：`01a21280-39c6-76b4-869f-8edfbc9b23ff`。这一轮共有 134 次 tool_use、74 段 thinking，script 模式下还有 144 次内部调用。

根因有两层：

1. **SDK 按显示块截取实时窗口。** v1 view 只保留最后 150 个显示项（`KodaX/src/session-view.ts` 的 `SESSION_VIEW_ITEM_LIMIT`）。每个工具调用、每段 thinking 都单独算一项，截取不看轮次边界。一轮超过 150 项时，窗口从这一轮中间开始，提问被挤出窗口。
2. **Space 不能自己拼接。** ADR-010 规定实时 view 和保存历史分开显示、不能拼接，理由是两边的 item ID 属于不同引用范围（[ADR-010](../ADR/ADR-010-sdk-product-output.md) 第 15、24 行）。所以 view 一旦不包含最早的保存项，Space 只能在接缝处放一个切换来源的按钮（[`canOpenSavedPage`](../../apps/desktop/renderer/src/shell/ConversationStreamV2.tsx#L972)）。F144 的视觉窗口也把实时来源排除在外（[v0.1.47 设计](../features/v0.1.47.md#feature_144-windowed-continuous-transcript-virtualization)）。

最终效果：UI 拿不到一条可以连续翻阅的数据序列，“显示多少”被 SDK 的数据窗口替 UI 决定了。“111 个命令”也只是窗口里剩下的数量，不是这一轮的真实总数。

## 2. 分工原则

- **SDK 负责数据**：item 身份、顺序、分页、实时增量、身份空间何时失效。
- **Space 负责显示**：挂载哪些行、怎样按轮次分组和折叠、计数、锚点、阅读位置、内存预算。

SDK 的 150 项窗口在 v2 里只是一次订阅的传输上限（单帧不超过 8 MiB），不应再等同于“用户能看到什么”。

| 能力 | 出处 | 对 Space 的意义 |

| 稳定 ID（FEATURE_312）：同一条消息在 view、`history.read`、保存后、压缩后、滑出窗口后都是同一个 ID | 第 1176–1177 行 | 两个来源可以按 ID 合并，ADR-010 的主要否决理由不再成立 |
| `view.subscribe` 先给快照，之后发 `view.patch`；只有 `item.put/remove/append` 和 `set` 四种操作 | 第 390–405 行 | 增量更新，滑出窗口的项表现为 `item.remove` |

## 4. Space 设计

### 4.1 每个 session 一份连续 transcript

用一个有序集合替代现在的两份数据（view 一份、history 一份，见 [`productSessionView.ts`](../../apps/desktop/renderer/src/store/productSessionView.ts)）。这个集合由若干段组成，段与段之间有明确的空洞：

```text
Transcript { epoch, segments: Segment[] }
Segment    = 一段已加载、顺序连续的 item（按 SDK ID 去重）
Gap        = 两段之间已知存在但还没加载的内容，带有可以补齐它的游标
```

item 的三个来源与合并规则：

| 来源 | 规则 |
| --- | --- |
| 实时窗口（`view.subscribe`） | 窗口内的项以最新帧为准，始终是最后一段的尾部 |
| 滑出窗口的项 | 同一 `epoch` 内被移除的 `settled` 项原样保留，因为它仍在对话里；被移除的 `live` 项直接丢弃（provider 重试撤掉的草稿） |
| 历史页（`history.read`） | 按 ID 并入。ID 已存在时，窗口内的项优先；否则用历史页的项。历史页和已有段有 ID 重叠就连成一段，没有重叠就作为新段插入，中间记一个空洞 |

接缝只按 SDK 稳定 ID 判断，不按正文、时间或 outputId 推测。这一点和 ADR-010 的禁令一致：ADR-010 禁止的是推测式拼接，不是有身份保证的合并。

### 4.2 失效与恢复

| 事件 | 行为 |
| --- | --- |
| `epoch` 变化（rewind、切换分支、Host 重启） | 丢弃整个 transcript，用新快照重建，并重新读最新的历史页 |
| 同一 `epoch` 内重连或重新订阅 | 保留已加载的段，用新快照替换尾段，并和保留的项按 ID 重新对齐 |
| 历史游标失效（`resync_required`） | 保留已加载内容，从最新页重新读，直到和已有段重叠 |
| 旧条目没有 `inputId`/`outputId`（ID 带版本号） | 无法按 ID 合并。这一段作为只读的保存段显示，接缝处保留现有的显式浏览入口 |

### 4.3 用空洞替代来源切换

- 撤销“浏览历史消息”这种切换来源的按钮。空洞在原位显示为一行加载占位，滚动接近时自动补齐。
- 补齐方向由空洞的位置决定：空洞上方的段用 `newerCursor` 向下读，空洞下方用 `nextCursor` 向上读，直到出现 ID 重叠。
- 只有身份确实接不上时（旧条目、修订变化），才显示说明，并提供重新定位或返回最新。

### 4.4 按轮次显示

- 一轮从一个 user 项开始，到下一个 user 项之前结束，顺序由 transcript 决定。
- 当前轮的起点还没加载时，优先补齐通往这一轮起点的空洞。实时窗口里的项带 `runId`，可以用来判断一轮是否从窗口之前开始。
- 一轮的内容超出视口时，这一轮的提问在顶部吸附显示。
- 工具组计数按已加载的项计算。这一轮的起点还没加载时显示“至少 N 个”，补齐后显示准确数字，不再把窗口内的数量当作总数。

### 4.5 视觉窗口与内存预算

- F144 的渲染窗口扩展到整个 transcript，实时尾段也包含在内。正在输出的行沿用 F144 的规则，一直挂载。
- 数据层也设上限：已加载的项超过预算时，离阅读位置最远的段被卸载并改回空洞。ID 稳定，以后可以再补回来。预算用 F144 的万行样本实测后再定，不预先加配置项。
- 锚点继续用 F144 的“SDK item ID + 行内偏移”。

### 4.6 搜索、定位与修改历史的操作

- `history.search` 返回结果后，用 `around` 读回的页按 §4.1 并入 transcript，直接跳到 `locatedItemId`，不再单独打开一个定位窗口。
- Fork 和回退通过 `history.resolveTurn` 按 item ID 定位，不依赖窗口内序号。原有的 `entryId/sourceRevision` 校验等 v2 对应方法确定后再对照调整。

## 5. 需要同步修改的决策和文档

- **ADR-010**：补充一节，允许在同一 `epoch` 内按 SDK 稳定 ID 合并实时 view 和保存历史；仍然禁止按正文、时间推测拼接。
- **F144**：去掉“实时来源不进入渲染窗口”的约束。
- **用户手册**：在“浏览历史消息”和“返回最新消息”的相关说明中写入新行为。

## 6. 依赖 SDK 补充的事项

1. 客户端观察接口要暴露 `epoch`（或单独的 reset 回调）。现在 `HostSessionObserver.onView` 只给出整份 150 项视图（`src/host-protocol/host-client.ts` 第 70–75 行）；重连和 `view.reset` 也只表现为一份新视图。Space 无法判断保留下来的窗口外旧项是否还有效。
2. 契约文档写明：在同一 `epoch` 内，`settled` 项被移除只表示它滑出了窗口，仍在对话里。
3. 确认并测试：一个 Run 还在运行时，这一轮里已经 `settled`、但已滑出窗口的项，能否用同样的稳定 ID 通过 `history.read` 读到。读不到的话，运行中途打开长 session 会留下无法补齐的空洞。

## 7. 验收场景

| 场景 | 期望 |
| --- | --- |
| 单轮超过 150 项，session 全程开着 | 提问和这一轮的全部步骤连续可见；计数准确；不出现切换来源的按钮 |
| 单轮超过 150 项，运行中途才打开 | 尾部立即显示；向上滚动自动补齐到提问；计数在补齐前标为“至少 N 个” |
| 同一 `epoch` 内断线重连 | 已读内容和阅读位置保持不变，不重复，不跳动 |
| rewind 或切换分支 | 整体重建，不残留另一条分支的项 |
| 压缩 | 项和 ID 保持不变，阅读位置不动 |
| provider 重试撤掉草稿 | 被撤掉的 live 项不残留 |
| 只有带版本号 ID 的旧会话 | 保存段可以读到；接缝处有明确的浏览入口 |
| 搜索后定位 | 结果并入同一 transcript，并能返回原来的阅读位置 |
| 万行样本 | 挂载数量、内存峰值、锚点漂移达到 F144 的目标 |
