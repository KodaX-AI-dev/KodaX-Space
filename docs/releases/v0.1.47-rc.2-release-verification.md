## Pre-tag repair history

main carried red `build` runs before this release. Neither item was turned green by a rerun.

- **Typecheck on `b328a617`, `4edd3ef1` and `339b8104` (deterministic on all four platforms)**: `TimelineMarker.tsx` and `rowDisclosure.tsx` used the global `JSX` namespace, which the Electron tsconfig does not provide (TS2503). Fixed by `7fcca00e` before this release preparation. Until then the unit suites behind Typecheck did not run in CI for those commits, so they were run locally on Windows first.
- **macOS Intel timing flake on `7fcca00e`**: `conversationTranscriptWindow.browser.test.ts` "windowing shows rows, not a spacer, when the live view is replaced under a reader" hit `page.waitForFunction: Timeout 30000ms exceeded` (4542 passed, 1 failed) while the same test passed on Windows, Ubuntu and Mac ARM at that SHA and locally on Windows. Its first occurrence among failed build runs since 2026-11-09. It passed on the release SHA on the same runner; no assertion, budget or timeout was changed.

## Release run history

- **Attempt 1 ([run 45299294645](https://github.com/KodaX-AI-dev/KodaX-Space/actions/runs/45299294645))**: source qualification, the four installers and the Windows, macOS Intel and Ubuntu acceptance jobs passed. The [macOS ARM acceptance job](https://github.com/KodaX-AI-dev/KodaX-Space/actions/runs/45299294645/job/138132252160) failed `sdk-history-navigation.spec.ts:309` "saved history search locates a question outside the live window and restores the selected result" on all three attempts (`expect(stream).toContainText('HISTORY_ANSWER_259')` after Escape timed out); the other 25 cases did not run. Release creation was skipped.
- **Re-run of the failed job only (attempt 2)**: the same case failed its first attempt again and passed on retry #1 (31 passed, 1 flaky); the windowing baseline passed. Publication then rechecked the source runs, the acceptance receipts and the installer checksums and created the release.
- The case was not reproduced locally on Windows against the packaged build, neither with the macOS runner's 1024×677 viewport nor with 4×, 8× and 20× CPU throttling. Three instrumented runs on the macOS runner (52 repeats, 17 failures) traced it: the Session's first follow to the bottom runs in an animation frame that the loaded runner delivers 300–650 ms late, and the case presses Ctrl+F before it, so the search records the top as its starting position; closing the search then restores that position. The search, scroll and windowing code is unchanged since rc.1. It is recorded as [Issue 256](../KNOWN_ISSUES.md#issue-256--closing-the-transcript-search-can-leave-macos-at-the-top-of-the-live-view-instead-of-the-newest-messages), ready for a fix that is not part of this release.
