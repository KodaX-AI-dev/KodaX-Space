## 确认的问题

### 1. P1：普通子 Actor 的请求、工具与 context target 不能稳定归到实际 turn

**触发与结果。** 普通根 Run 的原生子 Actor 不绑定 scoped credential lease 时，真实 `CodingActorSession.attach → spawnRoot → child runtime → OpenAI SDK` 完成并产生两条有 usage 的物理请求，但两条 observation 均没有 Actor attribution。实际 Actor 是 `/root/audit-child`、`turn_root_audit_child_1`；经过真实根/子 event wrapper 的工具执行 meta 却带 `turnId=root-turn`。子 context 保留 `contextKind=child`、实际 `agentId` 和 tokenBreakdown，但同样带根 turn，且没有 `childAgentId`。独立证据为 JSON 的 `actorWithoutLease.requests` 与 `actorWithoutLease.eventProjection`。

**采集至持久化的原因。** 采集 attribution 从 credential lease 读取；普通 Actor 在没有 parent credential lease 时直接执行，不建立 Actor attribution。根 Run observer 的默认 target 固定为根 Run，facts store 仅在 observation 含 Actor attribution 时改写。因此无 lease 子请求会存为根 Run target。工具的根 `withActivityMeta` 会以根 `nextMeta()` 覆盖传入子 turn；新增 collector 随后把 childAgentId 与被覆盖的 turn 组合为 actor_turn。context collector 只用 `childAgentId` 判别 Actor，预算 event 实际只有 `agentId`，因此普通根 Run 的子 context target 落回根 Run。

**影响。** Session 总 usage 仍可累计，但不能据这些 target 做可靠的根/子费用、上下文压力与执行归属视图。合法的 ambient/default 凭据路径不应改变统计身份。最小修复：Actor 执行归属独立于 credential lease 建立；子事件传回父 wrapper 时保留实际 child turn；预算 target 从已验证的 Actor/context 身份取得。补一个普通根 Run 的 native child fixture，逐项对照真实 actorPath/turnId、requests、tools、contexts。

**明确排除误报。** 首层独立 `client.agents.spawn` 的 fixture 通过真实 daemon 与公共 `statistics.readTools/readRequests/read`：一条工具为 `completed/succeeded`，请求和 context 的 target 都是实际 actorPath/turnId，见 `publicClientChildTools`。其 [显式 executionTarget:5408](C:/Works/GitProj/KodaX-AI/KodaX/src/sdk-runtime.ts:5408) 会补齐缺失 meta；不能把 `buildChildEvents` 省略 prepared/result turnId 单独当作首层独立 Actor 拆行错误。

### 2. P2：子工具实际 Sandbox observation 被 event 转发链丢弃

**触发与结果。** fixture 使用真实 `buildChildEvents`、`withLiveTurnAttribution`、`buildToolExecutionContext`、`executeToolCall`。执行 handler 时 `ctx.reportToolSandboxObservation` 确实存在且被调用，但父 `onToolSandboxObservation` 从未收到。证据为 `childEvents.dispatchedReporterPresent=true`、`dispatchedReporterReachedParent=false`。

### 4. P2：已知无 wire hook 的执行中 custom operation 仍返回 complete coverage

**准确边界。** fixture 使用真实 `withProviderRequestCredential('custom-fixture', …)` 包装一个只等待 Promise、随后返回 usage 的 adapter operation，整个 operation 不调用 fetch。它已发出并持久化 provider_operation，尚未返回时 `statistics.read` 是 `coverage=complete`、`operationCount=1`、`physicalRequestCount=0`、`issues=[]`；完成后才切为 partial。证据为 `activeOperation` 与 `completedCustomOperation`。这不是把“任何执行中 native pending operation”都判为错误，也不是误判缺少 usage：native pending operation 可以随后细化为 wire fact，`requestsWithoutUsage` 与 coverage 各有语义。

**原因与影响。** observer 对所有 adapter 先发相同的 provisional operation fact；facts store 只在 provider_operation 终态或死 owner unknown 时添加 partial issue。对 fixture 中已明确只可观察 operation 的 custom adapter，长期运行期间，调用者会读到与“custom/CLI 内部 wire 不可观察时明确 partial”不一致的 complete。源码：[pending operation:98](C:/Works/GitProj/KodaX-AI/KodaX/packages/llm/src/provider-request-observation.ts:98)、[zero-wire completion:107](C:/Works/GitProj/KodaX-AI/KodaX/packages/llm/src/provider-request-observation.ts:107)、[partial only after started:117](C:/Works/GitProj/KodaX-AI/KodaX/src/execution-facts.ts:117)、[unknown recovery partial:57](C:/Works/GitProj/KodaX-AI/KodaX/src/execution-facts.ts:57)、[contract:91](C:/Works/GitProj/KodaX-AI/KodaX/docs/SPACE_SDK_SEAMS.md:91)；绑定 [本轮 diff snapshot](./kodax-space-sdk-seams-completion-evidence.json)。

**最小修复与选择点。** 对已知 custom/CLI operation-only adapter 在 admission 时明确弱边界；native provisional operation 可以另保留“等待 wire 细化”的语义。若决定 complete 仅表示已结束 operation 的采集完整度，则需调整本轮契约并给执行中状态另一个质量字段。不能仅把所有 native started 临时标记永久 partial；当前 partial 会持久化且不会随 wire 细化恢复。
